# Real weights on RunPod — 2026-11-25

FastH3 V2 (`FastVideo/FastVideo-FastH3-8-Step-V2`, the `h3-8step` bundle on the
`fv-weights-h3-ltx-500` volume: bf16 transformer, MiniMax-H3 VAE and audio VAE) and
`taeh3.safetensors`, exported and run on a RunPod pod: RTX 4090 24 GB, 32 vCPU, 124 GB RAM,
Ubuntu 24.04. Software: litert-torch 0.8.0, ai-edge-litert 2.1.2, torch 2.9.1+cu128.
The pod was driven with `scripts/runpod/{pod,remote}.py`; every number below is from the
`out-N.log` files of that session. The fastwan-litert run of the same day is in
`fastwan-litert/docs/runs/`.

## Prompt encoding

The volume has no h3-rs gallery, so the prompt was encoded with h3-rs itself
(`cargo build --release -p h3-cli`, CPU backend, Qwen3-VL streamed from the volume):
`h3 encode --backend cpu --encoder stream --model-dir /workspace/h3-rs/h3` — about 6.5 min
for one 33-token prompt (the 64 GB bf16 encoder streamed from the network volume; the
binary was built without CUDA and the container has no usable Vulkan device for wgpu); `prompt_embeds [33, 5120]` f16 + `token_tags`, read by
`h3-litert generate --prompt` unchanged.

## Export

`h3-litert export --variant fasth3-v2 --model-dir /workspace/weights/h3-8step --tae
taeh3.safetensors --size 256x256x22 --weights f16 --jobs 4`

| part | graphs | size | wall (4 workers, the pod shared with two other jobs) |
|---|---|---|---|
| text refiner, buckets 128 / 256 / 512 / 1024 rows | 4 | 4 × 1 597 MB | 252–320 s each |
| embeds, heads | 4 | 3 MB | 4–7 s each |
| DiT block (qkv + post), per block in a worker | 100 | 2 × ~280 MB | qkv 47–120 s, post 75–114 s (4 workers, shared pod); 9 s + 16 s alone |
| attention (11 row counts) | 11 | weight-free | 2–28 s each |
| VAE decoder: `vae_dec_in`, 40 ViT blocks, `vae_dec_out` | 42 | 40 × 134 MB | 30–60 s per block |
| audio VAE decoder / encoder | 2 | 131 / 173 MB | 345 s / 66 s |
| TAEH3 (256x256, 5-frame chunks) | 1 | 20 MB | 28 s |
| AdaLN table (6 timesteps × 50 blocks) | 1 | 175 MB | 1 s |
| whole export (`--no-encoders`) | 160 | 50.1 GB | four runs, see below |

Three things this export taught the exporter:

- **bf16 shards.** safetensors' numpy reader refuses bf16; both ports now read checkpoints
  through the torch reader.
- **The f16 flag.** The first run wrote dynamic-range int8 graphs under the f16 label (the
  converter flag was passed as a dotted key); it was stopped at 36 files and restarted with the
  nested flag. Details in the fastwan-litert report of the same day.
- **A 61 GB cgroup.** `free` shows the host's 124 GB, but the pod's memory cgroup is 61 GB
  (`memory.limit_in_bytes`), and the OOM killer took worker processes mid-block (each worker
  peaks at 10–13 GB converting one 280M-parameter block; four of them plus the other jobs on the
  pod crossed the line). `multiprocessing.Pool` then waits forever for the lost tasks. The
  exporter now watches its workers, restarts the pool for the missing blocks, and has
  `--resume`, which skips every graph already on disk (the 39 GB of finished graphs were kept;
  the 7 missing blocks and the tail graphs were converted by a second run with `--jobs 3`).
- **The converter keeps memory.** A process that converts graphs grows by roughly 0.4–1 GB per
  graph it has converted (the parent reached 27 GB over the 40 VAE blocks; a `--jobs 1` block
  pass grew 1 GB per block). The second resume died at the keyframe encoders when the whole
  container hit the limit and was restarted (the disk survived). The export finished on the
  fourth run with `--no-encoders` (T2VA needs no encoder; the Conv3D encoder graphs at
  256x256 are the largest single conversions). Blocks now get a fresh process each
  (`maxtasksperchild=1`), which bounds the pool's memory to one block's conversion per worker.

## Parity against the PyTorch modules (`python/scripts/parity_blocks.py`)

The whole DiT in f32 is 56 GB and the pod's cgroup is 61 GB, so the uncut end-to-end
reference (`parity_real.py`, written for this run too) cannot run here. `parity_blocks.py`
instead checks every graph of the export against the PyTorch module it was cut from, one
block at a time (512 real rows of a 1024-row chunk, the export's own AdaLN rows, a real
RoPE table): 420 s for the whole export, 7.6–7.9 s per block, peak RSS under 10 GB.

| graph | relative error, f16 graph vs f32 torch |
|---|---|
| `text_refine_{128,256,512,1024}` (real rows) | 1.3e-4 – 1.5e-4 |
| `embed_video`, `embed_audio` | 6e-8, 5e-8 |
| `head_video`, `head_audio` | 1.2e-4 |
| AdaLN head rows of the ladder (`adaln.safetensors`) | 1.6e-4 |
| 50 × `block_NN_qkv` (q, k, v) | ≤ 8.1e-5, ≤ 8.1e-5, ≤ 1.2e-4 |
| 50 × `block_NN_post` | ≤ 2.6e-4 (worst block) |

That is f16 weight rounding and nothing else; the cut itself (row chunks, padded text rows,
the additive key mask, head groups, the precomputed modulation table) is covered end to end
by the tiny fixture at 1e-3 in CI and, for FastWan at real width, by the f32 run in the
fastwan-litert report of the same day (8.7e-5 on the latent after three steps).

## Generation

`h3-litert generate --graphs graphs/h3-f16 --prompt gallery-h3/01-…safetensors --size 256x256x22 --seed 7`
on the CPU (XNNPACK, 32 threads), pod otherwise idle:

| stage | time |
|---|---|
| prepare (text refiner bucket 128, layout, noise), 555 packed rows | 3.2 s |
| one DiT forward (50 blocks × qkv + post, 8 head groups of attention) | 463–470 s |
| 8 forwards (FastH3 V2 ladder) | 3 729 s (62 min) |
| VAE decode (ViT decoder, 40 blocks, 22 frames) | 32.4 s |
| audio decode (BigVGAN, 0.93 s stereo at 32 kHz) | 4.3 s |
| whole run (peak RSS 8.3 GB) | 3 771 s |

A forward costs ~9.4 s per block at 555 rows, and most of that is not arithmetic: with
`--resident 2` every step re-opens 50 block graphs (560 MB of f16 constants each, unpacked
to f32 and packed by XNNPACK on open). Keeping all 50 open would need more than the pod's
61 GB cgroup at f16 (the Kotlin / Swift / web runtimes have the same knob). The int8 /
int4 weight-only exports halve / quarter that traffic; they were not run in this session.

The TAEH3 preview path (`--preview`) shares the denoise and was not run a second time.

## GPU accelerator notes (ai-edge-litert 2.1.2 on Linux, WebGPU backend)

The tiny fixture's graphs compile on the GPU except `vae_enc_*`, `vae_dec_out` (Conv3D /
the 3-D unpatchify), `avae_dec_*` (the batch-folded 1-D transposed convolutions) and
`taeh3_*`; `Graph` falls back to the CPU interpreter per graph, so `--accelerator gpu` runs
end to end with those parts on the CPU.

## Files

`parity-blocks-f16.json` is the per-block parity report; the PNGs are the first / last frame of
the clip.

## What was not run

- The uncut end-to-end PyTorch reference at real width (56 GB f32 vs a 61 GB cgroup);
  `python/scripts/parity_real.py` is there for a machine with the memory.
- Any LiteRT graph on the GPU (the pod's Vulkan ICD does not load; see the fastwan-litert
  report); the Android / iOS / web runtimes against these graphs.
- The keyframe encoders (`--no-encoders`), so FL2VA / Ref2VA conditioning, and the other
  variants on the volume (`fasth3-trim-8step`, `fasth3-omni-8step-v1`, `pika-h3-flex`, the base
  model, the LoRA variants).
- int8 / int4 weight-only exports, the TAEH3 preview run, and the default 1344x768x124 canvas
  (its attention graphs and VAE tiles export the same way; the pod's CPU budget did not).
